工具名称与账户背景分开：`codex` 来源读取 `.codex/sessions/**/rollout-*.jsonl`，工具列表、详情与检测提示统一称为 Codex；它不是普通 ChatGPT 对话导入器。用户配置的 ChatGPT 套餐仍是独立的声明订阅背景，不代表这些会话均由该套餐付款。保留来源 ID 与现有配置键，不因修改展示名称重写历史归属。

DSH 压缩日志的扫描入口在返回前确认所有事件批次写入，包括最后不足 512 条的批次；失败抛错，不推进文件检查点，并记录文件级采集故障。已写入的前批在重放时去重。有效压缩帧、尾批失败与截断帧已用真实 SQLite 故障注入验证，但这不证明真实用户日志的覆盖完整性或长期采集健康。

菜单的金额观察区分成功为空与读取失败：前者隐藏金额行，后者显示本地化“不可用”，不能把失败伪装成无消费。主菜单与菜单栏复用该状态及格式，金额保留一位小数；活动汇总和金额观察的健康错误使用独立键，只能由对应读取成功恢复。菜单故障逻辑已有回归，实际错误界面与持续刷新仍须运行验收。

菜单刷新遵守最新请求所有权：顶部 Pulse 菜单、Dock 共用数据菜单和菜单栏各自保存刷新代次，较早请求即使晚完成也不能发布旧数据；顶部菜单还校验菜单对象身份，不写回已经替换的旧菜单。脉搏变化走同一刷新路径，不让轻量更新和完整重建相互覆盖。读取期间不预先清空顶部菜单；代次机制已有异步乱序回归，但实际菜单快速操作仍需运行验证。

消费声音的限次是提示次数，不是事件数或计费次数。全局静音、消费开关关闭、零／负／非有限音量时不预占额度；运行时首段音频成功启动才提交次数和合并窗口。素材缺失或播放器拒绝播放不提交，连续提示的第二段仍须重查当前设置和取消代次。零／无效音量决策已有回归，实际声音启动、失败和一键停止仍待 macOS 运行验收。

声音强度只接受当前有效的脉搏；过期或未来快照不能把新消费提示升级为连续强提示，但真实新活动仍可产生普通提示。系统时钟回拨时，未来的播放时间不用于限次或合并窗口，避免额度一直被占住。这些时间边界已做决策回归，不能替代睡眠唤醒或硬件声音验收。

当前脉搏查询有独立 `pulse.current` 健康状态，对应成功才清除。查询失败可保留尚未到期的既有观察，但不更新其观察时间；原有效期结束后返回未知，不制造休息状态。配额等子查询即使内部返回空值，其失败记录也会使脉搏整体读取失败，不能把失败当作成功的无活动。该失败／恢复及缓存到期行为已用注入源回归验证，实际错误界面和连续采集仍待运行验收。

工具和仓库的圆图份额使用明确的 `tokens` 字段，分组只合并词元数量，不用于金额分配；仓库身份仍是完整路径，与显示名称分离。未被调用的旧 CPL 引导、美元总额卡片及旧供应商圆图辅助代码已删除。来源余额等真实金额观察没有因清理词元圆图而删除，不能混同两种信号。

减少动态效果遵循 SwiftUI 系统环境：仪表盘首次进入直接显示完整内容，不从零缩放；切换设置会撤销待执行的进入动画，健康说明／仓库展开／详情展开不使用弹簧或位移动画。数据和入口仍即时更新，不因关闭动画延后反馈。源码及构建已验证，实际系统设置切换仍属于运行验收。

工具详情的会话分组也经过当前开发目录／Git 根授权边界，不能直接把历史工作区路径显示为仓库。无归属或不再授权的会话仍保留在未归属组，身份和词元不删；仅在读取后的副本归一化，不重写原始路径。会话代表路径仍取所选时段首条记录，不代表全部涉及仓库；同一时刻的代表路径和最近输入用事件 ID 确定顺序。真实临时 Git 仓库与 SQLite 回归已核对这些边界，真实详情列表仍待运行验证。

Git 根归属不仅检查 `.git` 标记：候选根须经 libgit2 只读打开，并确认工作树根与候选路径一致。空标记、损坏的 gitdir 指针和不存在的工作路径不能成为归属依据；linked worktree 则按自身工作根处理。编辑器路径检测复用同一判断，不保留第二套宽松规则。libgit2 初始化引用按本地库头文件的计数契约成对释放，不更改仓库内容。真实临时仓库与 worktree 已验证，用户目录权限、损坏仓库的实际提示和大型数据性能仍须运行验收。

Git 扫描故障属于本地采集而非供应商 API，按完整仓库路径记录；同名仓库恢复不清除其他仓库故障，扫描或持久化失败可见，部分 diff 不冒充完整扫描。轮询异步等待状态加载，不同步阻塞调用线程；迟到的数据库快照与偏好回退只合并，不覆盖已经建立的实时仓库与扫描进度。退出监控范围会撤销该仓库的当前采集故障，不删除历史事实。这些源码约束和健康隔离回归不替代真实启动、故障重试或连续采集验收。

Git 初始化使用异步共享加载，只缓存成功；数据库未就绪或查询失败不算初始化完成，下次轮询重试，加载失败有独立健康键。并发轮询共享正在进行的加载，失败后不推进依赖初始化状态的轮询。该恢复门控已有回归，实际数据库就绪时序与持续采集仍待运行验证。

Git 监控列表持久化统一在串行后台队列执行，执行时读取最新内存集合，不让较早的新增任务在清理后重新写回旧仓库。事务同步仅增删 `gitmonitor_state` 的集合差异，保留仍在监控行的元数据和所有提交／活动历史；偏好回退同队列更新。列表保存失败独立报告，后续轮询重试，不由扫描成功清除。集合幂等、事务失败恢复和退出监控后历史保留已用 SQLite 验证，实际启动／退出并发仍须运行验收。

2026-09-17 实施事实：生产采集不再根据词元或模型价表生成金额；旧价格折算、回填、来源金额仲裁与估价／订阅摊销状态已删除。模型目录改为 `Resources/model-catalog.json`，仅保存名称与供应商，用于识别，不证明某个账户实际付款。用户原始历史金额字段保留但不进入新活动展示。金额观察仅来自余额等原始采样，月费仅为用户声明的独立背景；后文第 5 节中旧金额行为是历史审计，不是当前实现说明。当前尚未完成真实运行验收。

## 0. 产品目标：不是计费器，而是 AI 消费的脉搏

AI Pulse 不追求替代服务商账单，也不承诺完整、精确地还原所有 AI 花费。服务商掌握计费规则、套餐额度、缓存折扣与价格变化；持续追赶这些规则，会把产品拖回维护成本很高、仍无法保证准确的计量竞赛。

产品的核心任务是：

> 当用户正在大量使用 AI 时，让他及时、持续地感受到消费正在发生、强度正在升高，并能回看这些消耗伴随了什么产出。

这是一种感知产品，而不是审计账本：

- **正在发生**：此刻有 AI 活动，脉搏应出现。
- **强弱可感**：活动更密、更重或额度压力更高时，脉搏应增强。
- **会自然衰减**：活动停止后，脉搏应逐渐回落，不能停留在旧状态。
- **事实可追溯**：用户点开后能知道信号来自 token、余额、额度还是代码变化。
- **金额不虚构**：只有观测到真实账户金额变化时才显示金额；没有金额时就使用 token、额度或归因产出表达压力。
- **产出并列呈现**：代码变化是消费的对照与结果，不用于证明消费“值得”，也不折算成钱。

“Pulse”不是另一个成本公式。它是多个可观测通道各自归一化后的节奏状态，用于声音、颜色、触觉和动效；原始数字始终保持各自单位。

## 1. 数据语义：观测、派生、上下文与未知

旧版的 `exact / estimated / amortized / uncertain / incomplete` 是成本置信度，不能作为 2.0 活动事实的统一分类。现行代码已移除 `estimated / amortized` 枚举及活动计价入口；原始历史列可保留，不代表继续兼容旧展示或计算。2.0 数据语义区分以下四类：

| 类型 | 定义 | 例子 | 展示规则 |
|---|---|---|---|
| **观测 Observed** | 从客户端文件、git 或服务商响应直接读到的值 | 原始 token 字段、日志时间、余额快照、额度缓存、commit 增删行 | 可显示原单位，并注明来源与采集时间 |
| **派生 Derived** | 由观测值经过明确算法得到 | 余额区间净下降、tokens/h、相对个人基线、脉搏档位 | 必须能解释算法、时间窗和完整性 |
| **上下文 Declared** | 用户登记或本地目录预填的信息 | 套餐月费、账期、静音时段 | 不冒充实时消费；预填值与用户确认值要区分 |
| **未知 Unknown** | 当前观测通道无法回答 | 套餐真实边际成本、隐藏加价、服务端未暴露的额度 | 明确留空，不用目录价格填补 |

每条可展示数据还应携带四个正交属性，而不是只贴一个 `exact` 标签：

1. `source`：来自哪个文件、API 或 git 信号；
2. `observed_at`：何时被观察到；
3. `freshness`：当前、陈旧或已失效；
4. `completeness`：完整、区间净值、部分覆盖或未知。

“直接观察到”不等于“业务含义绝对准确”。例如余额快照是观测事实，但两次快照之间的下降只是一个区间净变化；日志中的毫秒时间戳也只是日志记录时间，不一定是服务商结算时间。

周期快照的 `readFailures` 记录本次统计读取失败项，独立于词元字段完整性。成功查询到空集合不属于失败；失败回退的空集合或零值不能被解释为没有活动。此状态随快照缓存和传输保留；缺少该字段的旧派生快照失效重建，不删除原始历史。仪表盘显示失败提示，主要词元／会话／活跃日读失败时显示“—”。这还不等于采集源健康监控：未采集到的记录、采集器停止及扫描覆盖仍需独立说明。

应用统计健康错误按“周期＋查询”管理，只能由对应查询成功恢复时清除；不能因其他统计成功而清掉故障。已健康的查询不重复发恢复通知，避免刷新触发无意义的 UI 更新。此机制描述查询健康，不能证明日志监听器或 Git 扫描器正在正常采集。

日志持久化故障使用独立采集错误键：事件按批次身份、读取位置按位置保存通道记录。查询成功或无关批次成功不清除事件写入失败。此状态反映已知故障，不等于监听器存活或完整覆盖证明。事件现于专用扫描队列同步确认数据库提交，再允许推进文件游标；事件批次失败保留旧游标，后续重放由事件去重。JSONL 游标只到完整行末尾，短读／未完成 UTF-8 行不跨过检查点；DSH 任一流式批次失败不推进文件游标。位置加载、保存、扫描和停止都由同一队列排序，主线程不阻塞等待；停止后排队的扫描退出且释放合并标记，后续启动可恢复。位置提交失败在扫描末尾重试，DB 尚未就绪的初次加载在启动重试；只读取 DB 检查点，不继承旧 UserDefaults 位置迁移。非法位置报错而不进行有符号／无符号崩溃转换。进程终止或位置保存失败可能重放已保存事件，而不应跳过未保存事件。旧游标可能已经跳过的历史与实际连续采集／停止仍需单独验证，不能据单元测试宣布全部历史完整。

工具详情的会话列表区分加载、成功为空和读取失败，并可重试；仓库产出失败不抹掉成功读到的会话。过时或取消的详情请求不覆盖新请求的结果。展开会话的轨迹仍须独立遵守观察时间和读取状态规则，不能以列表已收口代替轨迹验收。

针对旧写入顺序可能跳过历史的恢复，启动设置在本地数据库事务内将派生检查点归零并记录一次性“已准备重放”标记，不删除原始活动／金额／会话。标记和归零共同提交或回滚，按数据库而非账户偏好判断；此标记不代表文件全部读取成功。后续扫描去重及补充缺失字段，不复写既存原始金额或计数。启动历史扫描不产生消费事件，运行时提示只接受本次观察启动后、非未来、近五分钟内首次写入的真实记录。真实用户数据库恢复完成仍须通过文件覆盖与运行证据确认。

展开轨迹用于查看完整会话的上下文过程，允许包含所选周期之前的有效输入观察，但截止时刻与此次详情加载一致；因此完整轨迹不是周期词元汇总。未来与合成记录排除，模型使用截止前最近有效模型而非字符串最大值。轨迹查询错误单独提示并可重试，不伪装为成功的空轨迹；请求代次防止旧加载覆盖新展开结果。曲线只含归一化输入大于零的观察，包括仅缓存创建的输入；输出合计独立读取同一截止前的全部有效事件，包括仅输出记录。词元字段缺失时提示只汇总已知部分，仍不声称覆盖服务商账户全部活动。

## 2. 可用观测通道与诚实边界

### 2.1 本地日志：消费活动的主要脉搏源

已支持 Claude Code、Codex、aider、OpenCode、Qwen Code 与 DeepSeek Harness（v2/v3 日志）。可观察：

- 工具、模型字符串、会话 ID、日志时间；
- 来源特定的输入、输出、缓存读取／写入与推理分项；原始字段和归一后的观察总量分开处理；
- 日志携带的 cwd，以及从 cwd 解析出的 git repo；
- 事件到达的频率与最近活动时间。

边界：

- 字段来自第三方日志格式，格式变化会造成静默断流；“已解析”不等于“完整覆盖”。
- `model`、cwd 与 session 有时由周边上下文事件向后传播，不应称为无条件精确。
- 不存在“所有来源缓存都是输入子集”的通用假设。Claude／DSH／OpenCode 的输入与缓存读写互不重叠，总输入为分项之和；Codex／Qwen 输入已包含缓存，不重复相加。
- DSH／Codex 的推理词元已包含在输出内，不重复加入；OpenCode 日志将输出与推理分开保存，总输出需相加。[Codex 上游转换](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/sse/responses.rs) 将报告输出直接映射为 `output_tokens`，推理细项另存，不能重复加入。
- 统一由 `TokenAccounting` 处理 SQL 与 Swift 计算。新增 `cache_creation_tokens`、`reported_output_tokens` 和 `reasoning_tokens` 保留可用分项；旧记录通过可用原始日志补齐元数据，不改写旧输入／金额。
- 旧 DSH／Codex 输出曾被保存为输出＋推理的派生值，没有原始报告输出时不拿它作为可信输出；分项缺失的总量只代表已知观察，当前脉搏标为部分观察，不能冒充完整计量。所选周期通过 `ActivityCoverage` 保存已观察行数与缺失分项行数；未知计数不等于健康零用量，界面分别提示部分观察和完整性不可用。即使所有已捕获分项齐备，也不代表整个账户已完整覆盖。
- 来源依据：[DSH 官方记账定义](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/llm-streaming.zh.md)、[OpenCode 分项实现](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/session/session.ts)、[Claude 缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

日志 token 是活动强度，不自动等于实际金额。它应直接驱动消费脉搏，不应先乘目录牌价才能获得展示资格。

### 2.2 余额与累计用量 API：真实金额的机会性增强

API Key 可解锁余额或累计用量快照。诚实的语义是：

- 原币余额/累计用量快照：服务商响应的直接观测；
- 两次快照之间的余额下降或累计用量上升：**区间净消耗**；
- 发生时间：只能归属于两个采样点之间，不能伪装成逐事件精确时间；
- 若区间内同时充值、退款或发生非 AI Pulse 可见的消费，净差值不能解释各笔明细；
- 换算 USD 是独立估算层，原币值必须保留。

因此文案应使用“观察到余额减少 ¥12.40”或“本区间累计用量增加 $3.20”，而不是泛化为“这次调用精确花费 $3.20”。

余额数据可增强金钱压力，但不能成为所有工具都有的前提。删除 Key 后界面停止展示陈旧余额；是否保留历史观测应由独立的数据保留策略决定，而不是随凭据一起删除。

### 2.3 额度状态：压力信号，不是套餐身份证明

Claude 本地状态缓存和 Copilot API 可以提供利用率、触限状态与重置时间。它们适合回答“额度压力是否正在升高”，但存在以下边界：

- 缓存可能陈旧或字段缺失；必须展示 `updated_at` 与 stale 状态；
- 缓存存在不能证明当前仍有有效套餐；
- Claude 的 5h 与 7d 窗口是两个独立事实，不应只保存其中较高者；
- Copilot 数据来自内部接口，格式与可用性都可能变化；
- 额度百分比不能和 token 或钱直接相加。

额度利用率可以参与脉搏压力档位，但原始窗口必须分别展示，且陈旧数据不得继续驱动当前状态。

### 2.4 git 与编辑器会话：产出和弱归因

git 的 commit、added/deleted 与时间是本地仓库观测。AI 归因则是另一层：

- trailer 只能证明提交信息声明了某个协作者或生成工具，不证明该提交的所有行都由 AI 生成；
- 编辑器打开某 repo 与提交时间接近，只是弱时序关联；
- 未归因代码变化只作为产出对照，不进入 AI 消费强度；
- 归因行数可以作为“活动痕迹”兜底，但应统一标为 `attributed/uncertain`，避免用 `exact` 暗示逐行作者身份。

产出展示建议保留 added、deleted、net、commit 数与 repo；不计算 CPL，也不将行数换算成金额。

### 2.5 套餐与目录价格：上下文，不是实时消费

套餐月费、账期与目录价格最多是上下文：

- 用户亲自确认的月费可显示为“已登记固定成本”；
- 自动预填的目录价必须明确为“未确认”；
- 固定月费不进入实时燃烧率，不按天摊销成“今天花了多少钱”；
- 套餐内 token 不按 API 牌价制造美元金额；
- pricing catalog 可保留用于诊断、研究或明确开启的“API 等价参考”，但不得进入默认头条、通知、声音强度、Dock 徽章或跨端主指标。

## 3. 消费脉搏模型

### 3.1 四条并行信号

| 信号 | 原始单位 | 适用场景 | 是否可单独驱动脉搏 |
|---|---|---|---|
| 活动信号 | events/min、tokens/min | 有本地日志的工具 | 是 |
| 金额信号 | 原币/时间窗 | 有余额或累计用量 API | 是 |
| 额度信号 | 利用率%、距重置时间 | 可观测套餐额度的工具 | 是 |
| 归因产出信号 | attributed churn/time | 无日志但有弱归因的工具 | 仅兜底 |

四种原始单位永不求和。每条信号只与自己的近期历史比较，生成无量纲的 `0...1` 压力分数，再由 Pulse Engine 选择当前最可信、最新鲜的主信号并保留辅助信号解释。

### 3.2 脉搏不是金额估算

建议的状态模型：

| 状态 | 含义 | 感知反馈 |
|---|---|---|
| `resting` | 无近期活动或数据已陈旧 | 静止、冷色、无声 |
| `active` | 正在稳定使用 | 轻微脉动；按合并窗发出一次轻反馈 |
| `elevated` | 明显高于个人近期基线，或额度压力升高 | 更暖颜色、更紧凑节奏 |
| `intense` | 持续高强度或接近额度上限 | 强但受控的视觉/声音/触觉提醒 |

档位应来自个人基线，而不是全局美元阈值。tokens-only 工具也必须能进入 `elevated/intense`；活动停止后应由时间衰减回到 `resting`。

### 3.3 感知反馈原则

- 每一批新消费活动最多产生一次反馈，密集事件先合并；
- 强度主要由“相对自身平时是否异常”决定，而不是用目录价格决定金币单双响；
- 声音默认保持克制，用户可一键关闭，静音时段内不积攒到结束后突然补响；
- Dock、菜单栏、iOS、watchOS 与 widget 使用同一 Pulse Snapshot；
- 颜色、动画、声音和触觉表达同一状态，但不要求每个平台显示同一个数字；
- 降低动态效果时保留颜色/文字状态，去掉持续动画。

## 4. 展示出口

### 4.1 常驻出口：先让用户感受到

| 出口 | 第一信息 | 第二信息 | 不应出现 |
|---|---|---|---|
| 菜单栏 | 当前脉搏状态与会自然衰减的动效 | “正在使用 Codex · 12.4k tok/最近 10 分钟”；有真实金额时另列金额 | 无依据的 `$x.xx` 头条 |
| Dock | 脉搏颜色/短促跳动 | 可选今日活动徽章 | 用估算金额填环、固定显示估算美元 |
| watchOS / complication | `resting/active/elevated/intense` + 简短单位 | 额度临界或真实金额 | 复杂图表与混合单位 |
| iOS / widget | 当前状态、最近活动、今日主要事实 | 真实金额/额度作为条件式卡片 | 把旧 `todayCost` 当成统一真相 |
| 声音/触觉 | 新活动到达与强度变化 | 极少量里程碑 | 数据刷新声、补偿式连响 |

### 4.2 仪表盘：解释脉搏，而不是抢回产品头条

仪表盘回答“为什么我刚才感觉压力很高，以及这些消耗伴随了什么产出”：

1. 当前脉搏及来源说明：主信号、时间窗、相对个人基线；
2. 今日活动：正确去重的 token、会话、活跃时段；
3. 条件式金额：只展示原币区间净消耗和采样边界；
4. 条件式额度：分别展示 5h/7d 等窗口、更新时间和陈旧状态；
5. 产出：commit、added/deleted/net、repo；归因与未归因分开；
6. 采集健康：每个源最近成功时间、断流和格式异常；
7. 高级诊断：模型、工具、repo 分布；不再以价格目录覆盖率驱动主流程。

机器人头像继续作为稳定的信息骨架，但每个部位只表达一种语义：天线显示当前所选时段的完整周期词元均速（Today ÷ 24 小时、This Week ÷ 7 日、30 Days ÷ 30 日）；额头是当前时段词元、会话与活跃日；左眼是工具词元份额；右眼是获准 Git 仓库的词元份额；鼻子是 added/deleted 与 commit 等产出；嘴部是两条彼此独立归一化的时间节奏——词元活动与代码变化。本周固定为 7 个日槽位，30 天固定为 30 个日槽位；Today 的词元活动与代码变化都按真实事件时间进入 24 个小时槽位，不做平均摊派。任一节奏没有数据时仍绘制一条淡色分节基线，保持布局稳定并明确表达“当前为空”。头像内不显示美元，也不放月费。

三个时段均提供工具×模型和授权仓库分布；条件式原币金额与新鲜额度在头像外独立展示。30 Days 增加工具／订阅上下文；不要求用户填写账期起点或周期，也不要求登记所有月费。用户已声明的月费仅是固定投入背景，不是当前周期付款。余额下降是采样区间的账户净变化，不称为逐笔确认扣费。

### 4.3 日终回顾

收盘钟应是消费感的日终回声，而不是伪精确账单。建议内容：

- 今日活跃时长、正确去重的 token、峰值时段；
- 有真实金额观测时，附“观察到账户净消耗”；
- 有新鲜额度数据时，附当前利用率与下次重置；
- 今日 commit 与代码变化；
- 不包含 token × 目录价格、不包含按日摊销月费、不包含预测。

## 5. 当前代码审计：为什么已实现很多功能，使用感仍有距离

以下为 2026-09-13 的历史审计，保留以解释设计转向。后续源语义核查否定了原先所有缓存均为子集的假设；旧引擎、金额回填及部分聚合问题已在实施中修复。最新事实与尚未完成的门槛见 `docs/macos-v2-closure-plan.md`，本节不能直接当作当前缺陷清单。

### P0：先修数据与语义错误

1. **词元聚合忽略来源语义。** 历史实现曾统一相加缓存，之后又统一把缓存当作输入子集；两种全来源假设都不成立。须按真实字段关系计算，既避免子集重复加入，也避免互不重叠分项漏算，并核对推理是否已经包含在输出。
2. **历史金额并非“入库后不变”。** `CostBackfill.repairCacheSubsetPricing()` 会重算所有 `estimated` 行的已有 `cost_usd`，与“插入时点牌价、历史不重算”的文档口径冲突。
3. **余额时间窗边界会漏算。** `consumptionSpend` 与 `BurnRateEngine.fetchBalanceDeltas` 从窗口起点才取快照，没有读取窗口前的基准快照；第一笔区间差值会丢失。`combinedSpend` 已用 14 天 lookback 规避同类问题，但几条路径口径不一致。
4. **额度状态丢失信息且可能永久陈旧。** Claude 只把 5h/7d 中较高的一条压成单行；读取侧不返回 `updated_at`，也不按 freshness 失效，旧额度可能长期显示并参与理解。
5. **工具×模型聚合键不完整。** 查询选择 `source`，却只按 model/provider 分组；同一模型/服务商被多个工具使用时，SQLite 可能返回任意 source，矩阵会错误归因。
6. **归因的 `exact` 语义过强。** trailer 证明的是提交声明，不是逐行作者；当前 `GitMonitor` 将其写为 `exact`，同时又与 `PRODUCT_DESIGN.md`“归因恒 uncertain”冲突。

### P1：核心脉搏仍被估算美元绑架

1. **`BurnRateEngine` money-first。** 只要存在 `cost_usd` 就优先用 USD/h；而多数日志金额来自 token × pricing catalog。用户感受到的是目录估算，不是实际消费。
2. **tokens-only 永远只能是 normal。** 当前 tier 只比较美元基线；没有美元时 ratio 为 nil，token 或归因行数再高也只会得到 `.normal`，无法表达套餐工具的高强度压力。
3. **状态不会可靠地随时间衰减。** 状态项主要随 `.dataDidChange` 刷新。活动停止后如果没有新事件触发重算，滚动窗口虽然在数学上会过期，用户看到的火焰仍可能停在旧档位。
4. **声音强度仍依赖估算金额。** `CoinSound` 的 coin/double/rain 判断接收 `spendUSD`；日志事件的这个值来自目录牌价。高价模型会比高强度套餐活动更容易“听起来贵”。
5. **静音期间会累计并补响。** suppressed spend/tokens 在静音结束后合并进下一次决策，可能产生与“此刻正在消费”不一致的延迟强反馈。

### P1：各出口讲的不是同一个故事

1. **菜单栏与 Dock 把估算美元作为默认主数字。** 两者调用 `consumptionSpend(A 估算 + B 净差值)` 并直接显示 `$x.xx`，没有在状态项标题或 Dock 徽章标示估算。
2. **跨端 `todayCost` 语义不同。** Dashboard Snapshot 的 `todayCost/weekCost/monthCost` 来自 `combinedSpend(B + 套餐摊销)`；菜单栏/Dock/收盘钟使用 `consumptionSpend(A + B)`。iOS、watchOS 与 widget 又把 `todayCost` 当作统一美元事实。
3. **Dashboard 左圈混合时间口径。** 当前范围内的余额净消耗与整月固定套餐费相加成圆环总额；Today、This Week 与 30 Days 下都可能出现分母不一致。
4. **收盘钟仍是金额通知。** 当前只发送 `consumptionSpend + 峰值小时`，既缺 token/额度/产出，也把混合估算金额写成当日花费。
5. **“未计价 token”不是核心问题。** 当前计划把补价格目录与显示未计价 token 作为后续重点，但新方向下未知价格不再阻断消费脉搏；真正需要显性化的是采集是否新鲜、token 是否完整、当前信号为何升档。

### P2：已有能力没有形成体验闭环

- 已有 `ConsumptionEvent`、声音合并窗、Burn Snapshot、菜单栏、Dock、跨端字段、额度条和 git 归因，但它们围绕“金额优先的燃烧率”连接，尚未围绕“活动到达 → 脉搏增强 → 时间衰减 → 日终回顾”形成闭环。
- 仪表盘已有 token 头条、repo token 圈图、工具×模型 token 矩阵和额度倒计时，因此旧差距清单已过期；下一步不应继续堆图表，而应先统一语义与感知状态。
- `CostConfidence` 只覆盖成本，无法解释 token 来源、额度陈旧、余额区间完整性和归因强弱，导致 UI 很难诚实说明“为什么是这个状态”。

## 6. 下一步改进路线

### 阶段 A：计量语义归一（必须先完成）

目标：所有后续感知建立在没有重复计数、没有混用字段的事实层上。

1. 新建统一的 token 计算帮助器，替换所有 `in + out + cache` 聚合；补跨解析器与 SQL 聚合测试。
2. 将金额拆成明确字段：`observedSpend`（原币/区间）、`convertedObservedSpendUSD`（含换算率与来源）、`catalogEquivalentUSD`（仅诊断）、`declaredMonthlyCostUSD`。
3. 修复余额窗口 lookback，并用“首个窗口差值、充值与消费混合、usage-type provider”测试覆盖。
4. quota schema 分别保存各窗口和 `updated_at`；UI 标注陈旧值，并向 Pulse Engine 提供自动失效判断。
5. 修复 model/provider/source 的聚合键；统一 trailer 归因为 `declared` 或 `uncertain`。
6. 为 Dashboard Snapshot 新增语义明确的可选字段并提升 payload version；保留旧字段只用于兼容，不再扩散 `todayCost` 的歧义。

验收：同一批 fixture 在 Today、菜单栏、Dock、iOS、watchOS 中得到相同原始事实；cache token 不重复；任何美元都能追溯到余额/累计用量或明确标成非实际参考。

**实施状态（2026-09-13）：阶段 A 已完成。** 已落地统一的 `TokenAccounting`；余额查询带窗口前基线并覆盖余额下降、充值过滤与累计用量增长；额度按窗口独立持久化且携带新鲜度；模型聚合键与 trailer 归因已修正；删除 API Key 不再删除历史余额观测；共享快照升级到 `2.1.0`，新增真实区间金额、带来源的可选换算金额、目录等价参考和登记固定成本字段。未知币种不再按 1:1 写入新的语义字段。旧 `todayCost`、金额优先的 `BurnRateEngine` 及现有常驻出口仅作为兼容层保留，尚未完成产品体验转向，分别由阶段 B/C 处理。

### 阶段 B：用 Pulse Engine 取代 money-first BurnRateEngine

目标：没有余额 API、没有价格目录的套餐工具，也能产生真实、会衰减的消费压力。

1. 输入四条并行信号：活动、真实金额、额度、归因产出；每条记录 freshness 和 completeness。
2. 活动、真实金额与归因产出分别建立个人近期基线；额度使用服务商窗口上限作为天然基线。冷启动使用明确的通道内参考值兜底。先分别归一化，再选择主信号，禁止原始单位混加。
3. 实现基于时间的衰减与固定轻量 tick，使状态在无新事件时也能回到 resting。
4. 档位改为 `resting/active/elevated/intense`；记录 `reason`，例如 `token_rate_2_4x`、`quota_91_percent`、`observed_spend_spike`。
5. 声音与触觉由“新活动 + 档位变化”驱动；移除 token 牌价对单双响的控制，静音期间的数据不在结束后补响。

验收：构造只有 token 的高强度会话能够进入 intense；停止活动后在规定时间内自动降档；删除 pricing catalog 不影响脉搏；相同事件不会因模型目录价不同而产生不同声音。

**实施状态（2026-09-13）：阶段 B 已完成。** 新增 `PulseEngine`，活动 token、真实余额区间金额、额度窗口和不确定归因产出均保留原单位、基线、新鲜度与完整性；引擎只比较归一化后的通道分数，并由最强新鲜信号输出 `resting / active / elevated / intense` 与可追溯 `reason`。活动、金额和产出使用 7 天非空小时中位数，额度使用服务商 100% 上限；历史不足时使用通道内冷启动参考，价格目录不参与。近期事件按 10 分钟半衰期衰减，协调器每 30 秒只刷新派生状态，不扫描、不响铃。macOS 状态颜色和声音已改由 Pulse 驱动；声音只按档位分级，静音、限流和合并窗内事件均不累计补响。

### 阶段 C：重写常驻出口

目标：用户不打开仪表盘也能感到脉搏，同时不会把估算当账单。

1. 菜单栏以状态和短促动效为头条；次行解释主信号，真实金额条件式出现。
2. Dock 环改成当前脉搏/今日活动密度，不再用 `todayCost / prediction.dailyRate` 填充；徽章默认不显示估算美元。
3. iOS/watchOS/widget 改读 Pulse Snapshot 与语义化事实字段，不保留未发布 2.x 草案的降级路径。
4. 收盘钟改成活动、真实金额（如有）、额度（如新鲜）和产出的短摘要。
5. 为 Reduce Motion、声音关闭、静音时段和通知权限分别提供等价的非声音反馈。

验收：无 Key、只有本地日志时仍能完整体验脉搏；有 Key 时只是增加真实金额信息，不改变产品是否可用；所有出口对同一数据使用相同状态和解释。

**实施状态（2026-09-16）：阶段 C 已完成。** 首个正式 2.x 契约定为 `2.0.0`，原生同步 `PulseSnapshot`（档位、主信号、reason，以及每个通道的原值、单位、基线、归一化强度、新鲜度和完整性）；由于 2.x 尚未发布，删除了草案期 `burn*` 兼容字段与旧快照降级。菜单栏现在以档位为标题、以主信号为解释，并只条件式列出服务商观测到的原币金额；状态图标在新事件时短促闪动，Reduce Motion 开启时跳过动效但保留状态、颜色和文字。Dock 环只读取 Pulse 的归一化主信号，移除了 `todayCost / dailyRate` 和美元徽章。iOS、主屏 Widget、watchOS 表盘 Widget 均读取相同 Pulse。收盘钟改为活动 token、原币真实金额、新鲜额度和可归因产出的条件式摘要；声音关闭、全局一键静音或静音时段仍保留视觉通知，通知不可用时同一摘要仍写入菜单栏可见的最近收盘记录。

### 阶段 D：仪表盘解释层与采集健康

目标：让用户信任脉搏，而不是增加更多统计复杂度。

1. 首屏展示“为什么现在是 intense”与数据新鲜度；
2. 增加每个采集源最近入库时间、格式异常、权限缺失和覆盖盲区；
3. token、余额、额度、产出分区展示，不再强求一个跨单位总额；
4. 模型/工具/repo 细分移到深入分析区；
5. pricing catalog 与“API 等价参考”默认隐藏在高级诊断中。

验收：任一脉搏状态可在两次点击内追溯到原始信号；采集断流不会静默超过一个刷新周期；未知数据明确显示为未知而不是 0。

**实施状态（2026-09-16）：阶段 D 的首屏重构已落地，采集健康仍在进行。** macOS Dashboard 已保留机器人外形并采用上述稳定映射；原来的左眼 `$99`（余额区间金额与整月套餐费混合）已移除，工具词元份额取代金额圆环；工具×模型矩阵移出嘴部，并移除了重复的内层卡片；嘴部同时展示词元活动与代码变化节奏。所有紧凑数量统一支持 K/M/G/T 并保留一位小数，简体中文统一使用“词元”。Today 不再显示套餐摊销或用户填写的账期，30 天以工具使用事实表达订阅上下文。菜单摘要将 usage rows 的“calls”改成去重会话，固定月费不再参与 Today/Week 摘要。非合并 commit 数已作为独立产出事实进入 Today/Week/30 Days、仓库表和菜单摘要；它不与行数合并成分数，也不用于证明 AI 归因。所有 Git 产出查询均重新经过当前配置的开发目录和真实 Git 根目录边界，避免历史数据库记录污染当前视图。

设置中的通知已从“通用”拆为平级页面，系统通知、消费提示音和免打扰分别成组；声音包内三个提示音可单独试听。用户无需输入订阅开始日或周期长度，相应设置、快照字段和仪表盘周期进度已删除。

2026-09-17 收口修正：余额消费提醒和健康系统通知的默认提示音也遵守应用一键静音及静音时段；文字通知由系统通知开关独立控制。系统通知提示音不使用消费音包，也不受消费提示音开关／每小时次数限制控制。策略回归已验证，实际通知投递与听感仍待运行验收。

Today、This Week 与 30 Days 在内存中各自持有独立 `DashboardSnapshot`、加载任务与 generation。标签切换只改变当前投影指针；任一异步结果只能写回发起请求的时段槽位，不能覆盖其他时段，也不能触发其他时段的展示动画。三个时段会在首屏后分别补齐，避免把“当前视图”当作可被任意请求复写的共享数据容器。

仓库归属也已收紧为统一边界：日志 cwd 必须先解析到真实 Git 根，且 Git 根必须位于 `repo_search_dirs` 内；否则全局 token 仍保留，但 `repo_path` 写为 nil。历史记录不删除，查询时按同一边界过滤；移除开发目录后，监控器会停止轮询目录外仓库。因此 `Referenced…` 这类非 Git 工作区路径不会再进入仓库眼睛和仓库列表。

当前代码仍有三项明确债务：

1. 共享快照的旧 `todayCost/weekCost/monthCost/subDaily` 仍为旧客户端兼容字段，内部还会计算 B+C 旧口径；macOS 新首屏不再读取它们，但下一次跨端契约升级应将其标为 decode-only，并停止新写入。
2. `StatsService.repoBreakdown` 与菜单旧结构仍保留不可见的 catalog cost/CPL 计算；它们已不进入新 UI，但应进一步删除，减少维护服务商牌价的诱因。
3. Today 小时节奏目前来自可识别会话的起始小时；它表达活动节奏而非逐小时精确 token。后续应在共享快照增加明确的 hourly activity buckets，并携带覆盖度。

## 7. 建议实施顺序与文档同步

建议按以下顺序推进，避免再次出现“功能都完成了，但产品感仍不对”的情况：

1. 阶段 A 已完成；发布前继续用真实本地数据抽查 token、余额和 quota，不把 fixture 验证冒充真实账户验收；
2. Pulse Engine 已独立实现并通过自动化测试，未改大型 Dashboard；
3. 常驻出口已有代码与自动化验证，仍需实际工作流验收菜单栏／Dock；macOS 完整运行前暂停 iOS／watchOS／Widget 的开发与改进，不将暂停客户端验收列为本目标要求；
4. 阶段 D 首屏与仓库边界已完成；下一步补齐采集源健康、小时桶覆盖度，并清理不再展示的旧成本计算；
5. 最后基于阶段 D 的视觉结果更新发布截图与产品文案；
6. `PRODUCT_DESIGN.md` 与 `v2-implementation-plan.md` 已同步现行规则并归档旧完成记录；README、App Store 文案和截图仍须与最终运行结果核对。不得用旧阶段完成状态宣称当前 macOS 已达标。

这轮产品转向不以新增图表为目标。阶段 A 只完成可信事实层；整体转向真正的完成标志是：即使没有任何 API Key 和价格目录，用户仍能准确地感受到 AI 活动正在发生、强度正在变化、活动停止后脉搏会平息，并能看到这些消耗伴随了哪些可观察产出。
