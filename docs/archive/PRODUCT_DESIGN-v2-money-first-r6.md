## 1. 为什么重新定位（战略复盘）

### 1.1 市场事实已经变了

1. **孤岛用量已透明**：各家 AI 工具自带用量统计，插件生态又提供了一层。用户对自己"用了多少"心里有数。
2. **精确计量是军备竞赛**：服务商计量模式随时变动（计费口径、额度规则、余额 API），追逐它们的每一次变化是一个没有终点的维护黑洞。
3. **结论**：以"更精确的计量 + 更复杂的统计"为头条，是在一个已经拥挤、且对手（工具厂商）有主场优势的战场上作战。

### 1.2 校准：哪些事实不变

1. **孤岛有数 ≠ 全景有数**。Claude Code 报额度百分比、Codex 报 token、DeepSeek 报人民币余额——单位不通约。唯一能把它们放上同一把尺子的分母是"钱/时间"。碎片化在加剧而非收敛。
2. **厂商结构性做不了全景**。每家只拥有自己那一块数据，且动机相反——没有工具会主动让你"感觉"到自己在烧钱。
3. **精确与诚实是两回事**。v1.3 的 A/B/C 分级、"三档永不求和"、`CostConfidence` 五级置信度，这套哲学承诺的从来不是精确，而是**诚实的估算**。v2 废止的是"追精确"这个军备竞赛，不是计量层本身。

### 1.3 行为学依据

家庭能耗研究的经典结论：**实时反馈**（real-time direct feedback）相比月度账单能带来个位数到约 15% 的用量下降（Darby 2006 综述）。把抽象的累计数字变成即时的、可感知的反馈，人会自然调整行为。AI Pulse 的 job-to-be-done 由此从"记账工具"变为"**AI 花费的实时电表**"：不是替你记录，是让你**此刻感觉到钱在烧**，从而自然地校准工作方式。

### 1.4 三层护城河（本复盘的核心产出）

| 差异点 | 判断 |
|---|---|
| 计量精确性 | ❌ 放弃出售。军备竞赛，且用户在孤岛内已有精确数字 |
| 聚合完整性 | ✅ **别人没有的数据**——唯一能看到全景总账的地方，厂商结构性做不了 |
| 感知 / 行为 | ✅ **别人不敢做的事**——利益相反，工具厂商永远不会做；最情绪化、最可传播 |
| 统计复杂度 | ⚠️ 最弱的一个差异点：可被抄袭，且只讨好分析师型少数用户。降级为支撑 |

## 2. 价值栈（四层）

```
┌──────────────────────────────────────────────┐
│  L3 感知层   我此刻感觉到在烧钱吗？            │  ← 头条（新增投入）
│  金币声 · 燃烧率 · Dock 油表 · 收盘钟          │
├──────────────────────────────────────────────┤
│  L2 对照层   花掉的钱换回了什么？              │  ← 保留（独特分析）
│  花费图 + 代码变化图，两张独立、不相除          │
├──────────────────────────────────────────────┤
│  L1 聚合层   今天一共烧了多少？                │  ← 保留（地基/独占数据）
│  13 工具 × 三通道总账，跨孤岛唯一分母          │
├──────────────────────────────────────────────┤
│  L0 计量层   这笔消费是怎么观测到的？          │  ← 维持（诚实估算）
│  客户端观测为主（日志→token）· 服务端余额为辅  │
└──────────────────────────────────────────────┘
```

依赖方向自下而上：L3 依赖 L1/L2 的数据；L0 支撑 L1。**UI 与叙事的头条永远是 L3**；仪表盘是 L1/L2 的载体，是支撑页而非首页心智。

## 3. 感知层设计（v2 主形态）

### 3.1 核心概念：燃烧率（Burn Rate）

> **燃烧率 = 当前活跃时段的消费强度速率，只计按量部分。计价形态逐源退化：有钱计钱（USD/h），只有日志计 token（tok/h）。**

- **只计"燃烧"的消费**：API 余额消耗、token 计价花费计入；**订阅摊销不计入**——固定成本不在燃烧，这与 v1.3 "B/C 级只喂油表、C 级不进边际量"一脉相承。订阅仍出现在今日总账与对照层。
- **计价形态退化链（钱 → token → 归因行数）**：燃烧率优先以 USD/h 表达；纯套餐工具退化为 tok/h；无日志工具经 AI 归因（§4.6）退化为归因代码变化速率。**同形态内才求和，跨形态并列展示、永不折算混加**（延续"永不求和"铁律）。三级都不可得的工具诚实静默——不虚构响声，不虚构数字。
- **牌价折算（可选，默认关）**：用户可为套餐工具开启"按 API 牌价折算美元"，仅用于感知层的体感统一，显式标注"非实际支出"，永不进总账与对照层。这是对 v1.3 "虚构成本"禁令的**定点豁免**，范围仅限燃针。
- **与现有代码的关系**：`AnomalyDetector` 的"小时基线 ×3 告警"与 `SpendAlertService` 的 `spend_rate` 告警，本质都是燃烧率的特例。v2 将燃烧率提升为一等公民概念，由统一的 `BurnRateEngine` 计算，声音、视觉、通知全部消费同一个数。
- **诚实标注**：燃烧率是估算（`estimated`）时显示 `~` 前缀，与 `CostConfidence` 对齐。感知层建立在错误的数字上会摧毁信任。

### 3.2 声音设计：从"数据音效"到"金钱心跳"

现状（v1）：`CoinSound` 三个触发点——`ApiPoller` 检测到花费、`DataRefreshCoordinator` 数据刷新（60s 节流）、启动。**语义是"有新数据"，不是"花了钱"。**

v2 的唯一触发源是**消费事件**（usage_event / 余额差值落库），强度由燃烧率调制：

| 燃烧状态 | 声音 |
|---|---|
| 燃烧率 < 静默阈值 | 无声 |
| 正常消费事件 | 单金币（保留现有 `play(for:)` 金额分级：≥$1 金币雨 / ≥$0.1 双响 / 小额单响） |
| 燃烧率超 7 日基线 | 金币雨加密（密度调制，见防烦上限） |
| 日终 | 收盘钟 + 今日总账通知（可选） |

**防烦三原则（声音产品的生死线，硬约束）**：

1. **节流上限**：消费事件再密集，声音不超过 N 次/小时（沿用并收紧现有 60s 节流思路；燃烧率越高允许越密，但存在绝对上限）。
2. **勿扰**：应用一键静音与静音时段统一约束自动声音；启动钟默认关闭且可单独启用。当前不自动同步系统专注／勿扰状态，也不自动检测全屏演示，不对这两种状态承诺静默。系统通知是否呈现由 macOS 通知设置决定，与应用自播音效分开。
3. **独立音量**：感知音效音量独立设置，默认 50%，不跟随系统提醒音爆响。

**声音包**：`coin`（默认）/ 水滴（"花钱如流水"的本义）/ 收银机 / 油泵。可换、可关——**关闭永远是一键的**，且关闭不影响视觉燃烧层。

### 3.3 视觉燃烧：菜单栏与 Dock

- **菜单栏**：从"数字"升级为"状态"。常显燃烧图标（冷灰 → 暖金 → 火），数字其次；点开 = 今日总账 + 当前燃烧率 + 置信度。
- **Dock**：现有花费环保留，环色映射燃烧率（绿 → 金 → 红），角标数字不变。
- **iOS / watchOS**：complication = 燃烧率；手表端消费事件配触觉金币——"口袋里的油表"，零屏幕成本感知。

### 3.4 日终收盘

每天最后一笔消费事件后（或固定时刻），收盘钟 + 一条通知："今天 $12.40，燃烧峰值 14:00"。把"今天的钱"钉进记忆，形成每日一次的复盘节拍。

## 4. L0 计量层策略：观测点在客户端

### 4.1 核心原则：客户端观测优先（client-first）

**服务端是服务商的地盘，客户端是用户自己的地盘。**

- 服务端可变物：余额 API、点数/credits 规则、计费口径、重置周期——随时会变，追逐即军备竞赛。
- 客户端恒常物：**本地日志**（几乎所有编码工具都有，token 明明白白落在磁盘上）与 **git 历史**（代码最终落在我们的磁盘上）。它们不依赖任何服务商的恩赐，服务商改不动用户本地的文件格式生态。
- 因此：计量层的**根基**放在客户端观测；服务端余额 API 降级为**机会性增强**——有则是恩赐（`exact` 级），接口消失时自动退化为 token 计量，产品不受损。

### 4.2 消费的可观测形态（观测金字塔）

| 形态 | 回答什么 | 来源 | 角色 |
|---|---|---|---|
| **钱（USD）** | 消费的代价 | 余额 API 差值（`exact`）、token×牌价（`estimated`） | 燃针首选分母 |
| **token** | 消费的强度 | 本地日志解析 | **通用观测**：未必是费用，但**一定代表消费**；套餐工具唯一稳定可测的强度 |
| **AI 归因代码变化（行）** | 消费的痕迹 | `GitMonitor` × `EditorDetector` 归因（§4.6） | **兜底计量**：无日志、无余额工具的燃针来源；恒标 `uncertain` |
| **未归因产出（代码行）** | 消费的结果 | `GitMonitor`（`--numstat`，现有排除规则） | **对照物，不是计量**：人也在写代码，未归因产出永不折算为消费量（v1.3 反 CPL 哲学自洽） |

前三种进燃针（§3.1 退化链），第四种进 L2 对照层。**归因是把"产出"从对照物提升为计量物的唯一通道**——同一份 `code_change` 数据，归因了的算消费，归因不了的只算产出：一份数据、两种身份、互不混淆。

### 4.3 Coding Plan 与点数系统：明确永不建模

Coding Plan 服务商（Cursor、Copilot、Windsurf 等）以点数/credits 计费，三重死因决定服务端追踪不可行：

1. **无余额 API**——查不到剩余量；
2. **点数 ↔ 费用换算不透明**——不同功能扣不同点数，且与真实成本脱钩；
3. **周期性重置**——余额语义随时归零重来。

**v2 原则：永不建模任何服务商的点数系统。** 这类工具的消费观测一律走客户端（日志 token）；套餐月费走 C 级登记摊销，作为固定成本出现在总账与对照层，不进燃针。

### 4.4 多计价形态：schema 基本就绪

`usage_event` 表同时携带 `in_tokens/out_tokens/cache_tokens` 与可空 `cost_usd`，同行还有 `cost_source_id` + `cost_confidence`：

- **A 级日志事件**（Claude Code / Codex / aider / OpenCode / Qwen Code / DeepSeek Harness）：token + 金额双值俱全；
- **B 级余额事件**（DeepSeek / Kimi / 智谱等）：只有钱，无 token；
- **C 级登记工具**：目前**不产生任何消费事件**（§4.5 兜底链解决，归因行走 `code_change` 侧）。

`BurnRateEngine` 逐事件取可用形态计算：钱与 token 零迁移；归因行数仅需 `code_change` 增加两列（§4.6）。

### 4.5 缺口与盘点：C 级工具的消费观测

Cursor / Copilot / Windsurf 目前是纯登记制，燃针对它们是盲的。兜底链三级依次尝试，**逐工具独立定级**：

1. **本地日志**：Cursor 的本地 state 数据库、Copilot 的本地扩展日志等是否可**稳定、跨版本**解析（P0 盘点第一项）；
2. **AI 归因代码变化**：日志不可采时，用 §4.6 的归因机制从 `code_change` 里分出"AI 写的那部分"，作为消费强度的兜底计量；
3. **盲区标注**：前两者都不可得，该工具在感知层**诚实标注盲区**（沿用 v1.3 "盲区显式标注"原则），静默优于虚构。

### 4.6 归因机制：三个信号与一条铁律

"只计量 AI 自己产生的代码变化"——归因强度决定计量资格：

| 信号 | 强度 | 机制 |
|---|---|---|
| **git 元数据自归因** | 强 | 提交 trailer（`Co-Authored-By` / `Generated-with`）等工具自带署名——自带提交的工具（如 Claude Code）零成本精确归因 |
| **编辑器会话 × 时序关联** | 中（`uncertain`） | `EditorDetector` 已能经 workspace storage.json → `git rev-parse` 把 Cursor/Windsurf/VS Code 映射到仓库；`GitMonitor` 写入 `code_change` 时若该仓库存在活跃 AI 编辑器会话，则打上归因标记 |
| **工具本地历史** | 中（`uncertain`） | 编辑器 Timeline / state 数据库记录逐次编辑来源，与 §4.5 日志盘点同源，粒度比 commit 更细 |

**铁律：归因不到 = 不计量。** 归因行恒标 `uncertain`，永不升格为 `exact`；排除规则完整继承 `GitMonitor` 现状（lockfile、生成目录、merge commit）。数据模型代价极小：`code_change` 增加可空的 `attributed_tool` / `attribution` 两列即可。

### 4.7 零配置启动（配置面与观测面同原则）

观测根基在客户端（§4.1），配置也应然：**以"检测"代替"登记"**。目标状态——安装 → 授权主目录 → 立刻看到第一个数字，四步引导坍缩为一步。

1. **工具：检测即启用。** 首启自动启用检测到的集成（`migrateIntegrationDefaults()` 已是现状），无需用户逐项确认。
2. **订阅月费：目录价预填，不要求登记。** 内置公开套餐价目录（`plans-catalog.json`，与 `pricing-catalog.json` 同模式的本地数据，**不构成外部服务依赖**）：检测到 Cursor 安装 → 自动预填标准价（如 Pro $20/mo），用户可无视、可改、可清空。月费仍只进总账与对照层（摊销、`amortized` 置信度），**永不进燃烧率**。
3. **API Key：从入门步骤降级为"增强"。** 移入设置折叠区，填了更精确（`exact`），不填照样跑。纯 API 直连用户（自己写脚本调 API，无任何编码工具日志）在客户端观测下天然全盲——诚实归入 §4.5 盲区链，不为其牺牲默认体验。
4. **套餐月费不再扩张登记面**（2026-09-12 决策）：未支持的套餐（如 GLM Coding Plan / ZCODE）**不做登记**——"支持不完"。花费提醒以客户端已存在的数据（日志 token、归因行数）为基础，精确金额只是锦上添花。此类用量以 token 形态进燃烧率（火焰有反应），总账金额留空并诚实标注；定价表不为套餐模型补造价格（§4.3 同源原则：套餐 token 无边际成本）。

**收益**：Time-to-value 归零；默认状态不持有任何密钥（"100% 本地"成为可验证事实）；B 级从"依赖"翻转为"馈赠"。

**总账叙事相应调整**：头条是**消费总账**（token / 估算金额 / 归因行数），订阅月费行是可选的上下文信息——这与 §3.1 "固定成本不在燃烧"一脉相承。

### 4.8 停止 / 保持 / 新增

**停止**：

- 为边缘服务商逐家撰写精确适配；追服务商计量模式与点数规则的每一次变更；任何场合宣称"精确"。

**保持（已经是行业少见的诚实设计）**：

- `CostConfidence` 五级：`exact`（余额差值）/ `estimated`（token×定价表）/ `amortized`（订阅摊销）/ `uncertain` / `incomplete`；
- A/B/C 三档永不求和；pricing-catalog 按 model 查价；未知模型只入总账不进细算。

**新增**：

- 置信度沿数据流上行到感知层（燃烧率 `~` 标注、总账卡片角标）；
- 燃针多计价形态（钱 / token / 归因行数并列，永不混加）；
- C 级消费观测兜底链（日志 → 归因 → 盲区标注，§4.5）；
- 零配置启动：检测即启用 + 套餐目录价预填 + Key 降为增强（§4.7）。

**定位语**：计量层的目标从"精确"改为"**诚实到足以支撑感知层**"；观测的根基从服务端搬到客户端。

## 9. 约束与风险

1. **烦人风险高于一切**：防烦三原则（§3.2）是硬约束，任何"更感知"的优化不得突破节流与勿扰。
2. **感知建立在诚实之上**：燃烧率必须带置信度标注；宁可显示 `~`，不可假装精确。
3. **不回头**：CPL 不回到头条（v1.3 已降级，勿反复）；计量精确性不再作为卖点宣传。
4. **隐私不变**：100% 本地处理，感知层不新增任何网络请求。
5. **性能红线不变**：闲置内存 < 80MB；燃烧率计算走既有小时聚合，不新增高频轮询。
6. **归因宁缺毋滥**：只计量 AI 归因的代码变化；未归因产出永只进对照层，永不折算为消费（§4.6 铁律）。

## 11. 兼容性审计：对 v1.3 与在研 2.0 的影响评估

> 回答三个问题：v2 会不会造成既有功能破损？是否需要重新设计？之前的工作和基础设施是否作废？
> 审计基线：`Sources/` 14.5k 行 + `Suites/`（iOS/watchOS/widget）3.1k 行 + 测试 2.3k 行（163 用例）。

### 11.1 结论

1. **v2 是叙事与优先级的重排，不是架构重构。** v1.3 的代码分层与 v2 四层价值栈几乎 1:1 对应（§11.2），数据流 `Ingest → Store → Engine/UI` 原样成立。
2. **触及面很小且以增量为主。** P0/P1 直接触及约 1.2–1.4k 行（≈7%），无 schema 破坏、无 CloudKit 结构变更；**净删除语义 < 50 行**（`playForDataChange` 的"数据刷新音效"）。
3. **既有基础设施在 v2 下更值钱。** 13 集成、6 个日志解析器、定价目录、余额轮询、DB 与同步——正是感知层的燃料。被降级的是"未来的计量精确化计划"（尚未建造，无沉没成本）。

### 11.2 架构对应：v1.3 数据流 = v2 价值栈

| v1.3 代码层 | 对应 v2 层 | 处置 |

| `LogWatcher` + 6 解析器（A 级） | L0 客户端观测（根基） | **原样保留** |
| `ApiPoller` + `ProviderRegistry`（B 级） | L0 服务端机会性增强 | 保留，优先级下调（§4.1） |
| `SubscriptionRegistry`（C 级） | L0 登记制 | 保留 |
| `CostSource` / `CostConfidence` / `Database` | L0 账本与置信度 | 保留，置信度上行到感知层 |
| `StatsService` + `GitMonitor` | L1 聚合 + L2 对照 | 保留；`GitMonitor` 小幅扩展归因 |

### 11.5 诚实的代价清单

- **废弃**：`playForDataChange` 的"数据刷新 ≠ 花钱"音效语义（启动钟降级为可关）。
- **降级**：未来 roadmap 中"计量精确化 / 统计维度扩展"类工作的优先级——这是计划调整，不是沉没损失。
- **测试**：163 个既有用例断言的行为全部保留；新增用例集中在 `BurnRateEngine` 与归因打标。
- **迁移**：P0/P1 无任何数据迁移；CloudKit schema 不变。
